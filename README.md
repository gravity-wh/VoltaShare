## 一、体系摘要

### 1.1 核心判断

单卡环境不具备硬件切分能力，且 V100 不支持 MIG，因此资源复用只能通过三种软件模式实现：

| 模式 | 机制 | 适用场景 |
|---|---|---|
| 互斥独占 | 文件锁，全卡独占 | 训练、批处理、性能测试 |
| 时间片预约 | 预约表 + 锁校验 | 已知时长的任务、调试 |
| 服务化共享 | 常驻推理服务，多客户端复用 | 推理、演示、多人调用同一模型 |

其中服务化共享是提升有效计算占比的主要手段：模型加载为固定开销，重复启动将导致该开销被多次支付，同时显存被多份模型副本占用。

### 1.2 能力边界

以下为设备与生态的客观约束，方案设计不得与之冲突。完整依据与应对见管理体系文档 §2.2。

| 约束 | 影响 |
|---|---|
| 单卡不可分 | 并发只能靠时间复用或服务共享 |
| 不支持 MIG | 无显存硬分区手段 |
| SM70 无原生 bf16 / FP8 | 强制 fp16；FP8 量化模型不可用 |
| FlashAttention 2/3 要求 SM80+ | vLLM 回退 XFormers 后端，注意力性能下降 |
| AWQ 与 Marlin 要求 SM75+ | 量化路线限定 GPTQ 或 GGUF |
| CUDA 13 起不支持 SM70 离线编译 | 工具链固定于 12.x |
| 580 驱动为最后一个支持分支（LTS 至约 2028 年） | 体系按 18 至 24 个月不更换硬件设计 |
| 16 GB 显存上限 | 7B 模型须量化，fp16 不具实用价值 |
| 内核态驱动为全机单点 | 驱动故障将导致全部 GPU 服务失效，只能降低概率并压缩恢复时间 |

### 1.3 单卡 16 GB 的容量结论

| 模型规模 | fp16 | 4bit |
|---|---|---|
| 1.5B | 可行 | 可行 |
| 3B | 可行 | 可行 |
| 7B | 不可行（权重 14.2 GiB，仅余约 4K 单序列） | 可行（8K × 8 并发） |
| 14B | 不可行 | 勉强可行 |
| 32B | 不可行 | 不可行 |

推导过程与 KV Cache 计算见管理体系文档 §5.4。

## 二、快速开始

```bash
chmod +x scripts/*.sh

./scripts/gpu-who.sh                     # 查询当前占用：人员、显存、运行时长、命令
./scripts/gpu-run.sh --note "说明" -- python train.py   # GPU 任务统一入口，自动排队
```

`gpu-run.sh` 以 `flock` 实现互斥：抢锁失败时打印当前持有者并阻塞排队，退出时自动释放。脚本面向 Linux（依赖 bash 与 util-linux），在无 `flock` 的环境中降级为直接执行并告警。
