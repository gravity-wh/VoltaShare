## 1 范围与目标

### 1.1 背景

本环境为一台单主机 Linux 服务器，配备单块 Tesla V100 16GB 计算卡，由 3 至 5 名使用者共享。共享行为发生在三个维度：时间（同一张卡的不同时段）、环境（同一操作系统上的不同软件栈）、数据（同一文件系统上的不同数据集与权重）。

在缺乏硬件隔离手段的前提下，上述三个维度的共享必然产生冲突。本文件的目的不是罗列冲突现象，而是建立一套可执行、可审计、可演进的秩序：明确能力边界，规定每一层的职责与控制手段，并以可观测指标驱动体系的演进。

### 1.2 目标

| 编号 | 目标 | 验收方式 |
|---|---|---|
| G1 | 环境可复现 | 任一使用者在任意时刻可将运行环境重建至确定状态，重建耗时 ≤ 30 min |
| G2 | 资源使用可归属 | 任一时刻 GPU 的占用者可映射到具体人员、任务与时间窗，映射缺失率 = 0 |
| G3 | 冲突可控 | 以周为单位统计，资源冲突事件 ≤ 提交总数的 5% |
| G4 | 故障可恢复 | 驱动级故障发生后，全部服务恢复耗时 ≤ 30 min |
| G5 | 责任可追溯 | 任一故障可在 10 min 内定位到触发进程与触发者 |
| G6 | 演进有据 | 每一次架构升级由可观测指标触发，并留存决策记录 |

### 1.3 非目标

以下事项明确不在本体系范围内，列出以避免反复讨论：

1. **硬件级资源隔离**。单卡环境不具备该能力；V100 亦不支持 MIG。
2. **多节点调度与集群语义**。本环境为主机而非集群，任何依赖节点间迁移、分布式训练调度的方案均不适用。
3. **高可用与容错**。单电源、单卡、无冗余，本体系仅承诺"可恢复"，不承诺"不中断"。
4. **面向公网的服务发布**。所有服务限于内网或本机回环地址。

### 1.4 现状评估

对当前仓库能力与目标状态逐项比对，识别差距并定级。优先级定义：P0 为体系成立的前提，缺失则该体系不成立；P1 为运行两周内必须补齐；P2 为触发式建设。

| 能力域 | 现状 | 目标状态 | 差距 | 优先级 |
|---|---|---|---|---|
| 身份隔离 | 有书面约定，未确证已实施 | 一人一号，禁共用 | 未验证 | P0 |
| 环境隔离 | 有书面约定 | 每用户独立解释器与依赖树 | 无基线矩阵 | P0 |
| 资源互斥 | 已具备 `flock` 入口脚本 | 全量任务经统一入口 | 无强制手段 | P0 |
| 存储治理 | 无 | 目录契约 + 配额 + 审计 | 全部缺失 | P0 |
| 资产台账 | 内存与磁盘容量未登记 | 完整硬件与软件台账 | 信息不全 | P0 |
| 排队与预约 | 无（仅互斥锁） | 时间片预约与队列 | 全部缺失 | P1 |
| 服务化共享 | 无 | 常驻推理服务 + 统一接入 | 全部缺失 | P1 |
| 可观测性 | `gpustat` 手工查看 | 指标采集 + 看板 + 告警 | 部分具备 | P1 |
| 审计留痕 | 使用日志有，无留存策略 | 30 天留存 + 定期归档 | 策略缺失 | P1 |
| 治理制度 | 使用规约已具备 | RACI + 变更管理 + 事故复盘 | 三项缺失 | P1 |
| 配置管理 | 无 | 幂等初始化与配置基线 | 全部缺失 | P2 |
| 作业调度 | 无 | Slurm 单机（条件触发） | 全部缺失 | P2 |

### 1.5 设计原则

| 编号 | 原则 | 在本体系中的具体含义 |
|---|---|---|
| D1 | 最小权限 | 使用者不得持有 `sudo` 全权；提权以命令白名单形式授予 |
| D2 | 显式优于隐式 | 设备号、端口、数值精度、并发上限必须显式声明，禁止自动探测产生的不确定性 |
| D3 | 幂等与可重建 | 环境以声明式文件描述，重建过程可重复执行且结果一致 |
| D4 | 隔离不可信 | 假定一切软件隔离终将失效，故必须同时具备留痕与恢复能力 |
| D5 | 度量驱动演进 | 架构变更须由指标触发，并记录触发指标、决策与预期收益 |
| D6 | 成本与收益匹配 | 不使用与规模不匹配的组件；单机环境不引入容器编排系统 |

### 2.2 能力边界

以下约束为设备与生态的客观事实，任何方案设计不得与之冲突。将约束显式化，可避免反复尝试已被证明不可行的路径。

| 编号 | 约束 | 依据 | 对本体系的影响 | 应对 |
|---|---|---|---|---|
| C1 | 单卡无法在硬件层切分给多人同时使用 | 设备数量为 1 | 并发执行只能通过时间复用或服务共享实现 | §5.3 采用三种复用模式 |
| C2 | V100 不支持 MIG | MIG 为 A100 及之后架构的能力 | 无显存硬分区手段 | 以显存预算与并发上限约束替代 |
| C3 | SM70 无原生 bf16 与 FP8 | Volta 架构规格 | bf16 权重模型须转 fp16 加载；FP8 量化模型不可用 | 环境矩阵强制 `--dtype=half` |
| C4 | FlashAttention 2/3 要求 SM80 及以上 | 上游实现限制 | vLLM 自动回退至 XFormers 后端，注意力性能下降 | 显式固定 `VLLM_ATTENTION_BACKEND=XFORMERS`，并接受该性能水平 |
| C5 | AWQ 与 Marlin 量化内核要求 SM75 及以上 | 内核实现依赖 Turing 及以上特性 | AWQ 模型在该卡上不可靠；Marlin 不可用 | 量化路线限定为 GPTQ 或 GGUF，见 §5.4 |
| C6 | CUDA Toolkit 13.0 起不再为计算能力 7.5 以下架构提供离线编译与库支持 | NVIDIA CUDA 13.0 Release Notes | 无法用 13.x 工具链构建针对 SM70 的产物 | 工具链固定于 12.x（详见 C7） |
| C7 | 580 驱动分支为支持 7.5 以下架构的最后一个分支，属长期支持分支，覆盖期约三年 | NVIDIA 架构支持声明 | 该卡的可维护窗口至约 2028 年中 | 体系按"未来 18 至 24 个月不更换硬件"设计，选型以稳定优先 |
| C8 | 16 GB 显存为容量上限 | 设备规格 | 决定可承载的模型规模与并发数 | §5.4 显存容量规划 |
| C9 | NVIDIA 内核态驱动为全机单点 | 驱动架构 | 任一进程触发驱动异常将使全部 GPU 服务失效 | 无法消除，只能降低发生概率并压缩恢复时间，见 §5.8 |

### 2.3 寿命与选型倾向

由 C6 与 C7 可推出一个对选型有决定性影响的结论：该卡已进入生态维护期。因此本体系的选型判据不再是"性能最优"，而是"可在 2028 年前持续复现"。具体表现为：

1. 优先选择仍提供 SM70 预编译产物的发行版与镜像，而非需要自行编译的上游最新版；
2. 版本升级须先在独立镜像中验证，验证通过后方可进入共享环境；
3. 不追求与最新上游同步，允许落后一个小版本周期。

## 3 参考实践对标

### 3.1 对标方法

按能力域而非按项目对标。对每个参考对象回答三个问题：它解决哪个能力域；其中哪些机制可迁移至单机小规模场景；哪些机制因规模不匹配而必须裁剪或否决。

判别标准为：若引入成本（部署、学习、维护）超过其在该规模下带来的收益，则否决或推迟，并在表中记录理由，避免后续重复讨论。

### 3.2 对标清单

| 参考对象 | 类型 | 对应能力域 | 可借鉴机制 | 本项目结论 |
|---|---|---|---|---|
| NVIDIA DeepOps | 集群部署自动化仓库 | 配置管理、部署流水线 | 声明式清单、分阶段验证、部署后自检 | **裁剪采纳**：保留"清单 + 验证"思想，以单机 Ansible Playbook 实现，不引入其集群组件 |
| SchedMD Slurm | 作业调度系统 | 资源调度、配额、时限 | GRES 资源抽象、作业时限强制回收、优先级与公平共享 | **推迟（P2）**：机制正确，但交互式开发体验损失大；单卡场景用 §5.3 的轻量机制即可满足，触发条件见 §8 |

## 4 体系架构

### 4.1 分层模型

体系按职责分为七层。分层的意义在于：每层只暴露有限的接口，故障沿层向上传播时可被逐层拦截，变更的影响范围可被界定。

```
L6  治理层      角色与职责 · 变更管理 · 事故复盘 · 度量与演进
      ↑ 策略、配额、审计结论
L5  可观测层    指标采集 · 日志留存 · 告警 · 使用记录
      ↑ 指标、日志、审计事件
L4  服务接入层  端口规范 · 反向代理 · 认证 · 服务登记
      ↑ 服务端点
L3  运行时层    镜像 / conda 环境 · 版本矩阵 · 声明式重建
      ↑ 解释器与依赖树
L2  资源控制层  时间复用（锁 / 预约）· CPU 与内存限额 · 显存预算
      ↑ 设备使用权
L1  系统层      账号与权限 · 文件系统与配额 · 驱动与工具链
      ↑ 系统调用与设备节点
L0  硬件层      CPU · GPU · 内存 · 存储 · 供电与散热
```

### 4.2 层间契约

| 层 | 输入 | 输出（对上层承诺） | 失效表现 |
|---|---|---|---|
| L0 | 供电、环境温度 | 稳定算力与显存 | 降频、掉卡、不可纠正 ECC 错误 |
| L1 | 硬件 | 隔离的账号、可用的文件系统、可用的驱动 | 权限越界、磁盘写满、`nvidia-smi` 失败 |
| L2 | 系统层资源 | 互斥的设备使用权、受约束的 CPU 与内存 | 争抢、OOM、任务互相拖慢 |
| L3 | 设备使用权 | 确定版本的解释器与依赖树 | 依赖冲突、导入失败、行为不一致 |
| L4 | 解释器 | 可访问的服务端点 | 端口冲突、未授权访问 |
| L5 | 各层事件 | 可查询的指标、日志与归属关系 | 无法定位故障源 |
| L6 | 指标与事件 | 规则、配额、演进决策 | 规则失效、体系停滞 |

### 4.3 控制面与数据面

本体系中，控制面指账号、权限、配额、调度规则、镜像与配置；数据面指模型权重、数据集、推理请求与训练数据流。

二者分离的要求是：控制面的变更必须经管理员，数据面的读写由使用者自主完成。这样可在不牺牲使用效率的前提下，保证系统状态的可控性。

## 5 分项设计

### 5.1 身份与访问控制

#### 5.1.1 账号模型

| 类别 | 数量 | 权限 | 说明 |
|---|---|---|---|
| 使用者账号 | 每人一个 | 家目录读写、共享目录只读、经白名单执行有限管理命令 | 禁止共用，禁止共享密码 |
| 管理账号 | 一个 | 全部权限 | 仅用于系统维护，日常操作不使用 |
| 共享只读组 | 一个 | 共享目录读、执行 | 所有使用者账号加入 |

#### 5.1.2 提权控制

使用者默认不持有 `sudo` 全权。需要提权的操作以命令白名单形式授予，例如仅允许查看 GPU 状态与调整持久化模式：

```
# /etc/sudoers.d/volta-users
%volta-users ALL=(root) NOPASSWD: /usr/bin/nvidia-smi -q, /usr/bin/nvidia-smi -L
```

安装系统包、修改驱动、重启服务等操作由管理员执行，并记入变更记录（§5.9）。

#### 5.1.3 SSH 策略

| 项 | 要求 |
|---|---|
| 认证方式 | 仅公钥，禁用密码认证 |
| root 登录 | 禁止 |

| 组件 | 基线值 | 依据 |

| 方式 | 适用场景 | 声明文件 | 验收标准 |
|---|---|---|---|
| 容器镜像 | 需要固定版本、多人共用、服务化 | `Dockerfile` + 固定镜像摘要 | 空环境下 `docker run` 即可复现，耗时 ≤ 10 min |

禁止事项：

1. 在系统解释器中安装第三方包；
2. 对共享基线环境执行 `pip install --upgrade`；
3. 以 `latest` 标签作为生产依赖；
4. 依赖未固定版本的可传递依赖。

#### 5.2.4 重建验收

环境是否"可复现"不以"当时能跑"为判据，而以"在干净环境中重建后能跑"为判据。因此每次框架层变更后执行一次重建验证，记录耗时与结果，作为 G1 的实测依据。

### 5.3 计算资源调度

#### 5.3.1 三种复用模式

| 模式 | 机制 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|---|
| M1 互斥独占 | 文件锁，全卡独占 | 训练、批处理、性能测试 | 结果可复现，互不干扰 | 空闲期资源浪费 |
| M2 时间片预约 | 预约表 + 锁校验 | 已知时长的任务、教学演示 | 可预期，冲突可见 | 依赖执行纪律 |
| M3 服务化共享 | 常驻推理服务，多客户端复用 | 推理、多人数次调用同一模型 | 加载成本摊薄，显存可复用 | 需统一模型与参数 |

#### 5.3.2 模式选择判据

| 判据 | M1 | M2 | M3 |
|---|---|---|---|
| 任务时长 | > 30 min | 任意 | 持续 |
| 是否交互 | 否 | 是 | 是（经 API） |
| 显存需求 | 接近全卡 | 任意 | 中等且稳定 |
| 模型是否固定 | 否 | 否 | 是 |
| 推荐 | 训练与评测 | 调试与开发 | 推理与演示 |

#### 5.3.3 服务化优先原则

在单卡环境中，模型加载是纯粹的固定开销：一次加载耗时数十秒至数分钟，期间显存被占用但不产生计算。若多名使用者各自启动独立服务，该开销被重复支付，且显存被多个进程的模型副本同时占用。

因此确立以下原则：**当多人需要调用同一模型时，优先采用服务化共享而非各自独占**。该原则的量化依据见 §5.4.3 的显存账。

#### 5.3.4 实现路径

| 阶段 | 机制 | 强制力 | 说明 |
|---|---|---|---|
| P0 | `flock` 统一入口脚本 | 弱（可绕过） | 已实现，见 `scripts/gpu-run.sh` |
| P1 | 预约表 + 入口脚本校验 | 中 | 预约信息与锁持有者比对，不一致则告警 |
| P2 | Slurm 单机 | 强 | 由调度器强制，触发条件见 §8 |

绕过检测方法：将 `nvidia-smi` 采样得到的进程与入口脚本的使用记录比对，出现无记录进程即视为绕过，记入审计事件。

#### 5.3.5 并发上限

单卡环境下"并发"仅指显存维度。设定上限的目的不是限制吞吐，而是保证任一使用者的任务不会因他人显存溢出而失败：

| 场景 | 显存上限 | 实现方式 |
|---|---|---|
| 交互式开发 | 单进程 ≤ 8 GB | `torch.cuda.set_per_process_memory_fraction(0.5, 0)` |
| 推理服务 | 服务进程 ≤ 14 GB | 框架参数 `gpu_memory_utilization=0.85` |
| 训练任务 | 独占，不得与他人共存 | 入口脚本互斥锁 |

### 5.4 显存容量规划

#### 5.4.1 显存账模型

单卡 16 GB 的可用显存并非全部可用于模型，须扣除固定开销：

```
可用显存 = 总显存 − 驱动与 CUDA 上下文（约 0.3 ~ 0.5 GB）
                    − 框架与 cuDNN 工作区（约 0.3 ~ 1.0 GB）
                    − 显存碎片（约 5%）
```

在此之上的分配关系为：

```
可用显存 = 权重 + KV Cache + 激活值
```

其中 KV Cache 随上下文长度与并发数线性增长，是唯一可调节项：

```
每 token KV 字节数 = 2 × 层数 × KV 头数 × 头维度 × 精度字节数
```

#### 5.4.2 计算示例

以 Qwen2.5-7B-Instruct 为例（28 层、4 个 KV 头、头维度 128、fp16）：

```
每 token = 2 × 28 × 4 × 128 × 2 B = 57,344 B ≈ 56 KiB
4K 上下文单序列 = 56 KiB × 4096 ≈ 224 MiB
8K 上下文单序列 = 56 KiB × 8192 ≈ 448 MiB
8K 上下文 8 并发 = 448 MiB × 8 ≈ 3.5 GiB
```

该模型的 fp16 权重约为 14.2 GiB。由此可得：16 GB 卡上以 fp16 加载 7B 模型，扣除固定开销后剩余不足 1.5 GB，仅够约 4K 上下文的单序列，实用价值极低。**这是 §2.2 C8 的定量表述，也是量化路线成为必选项的原因。**

#### 5.4.3 容量矩阵

| 模型规模 | fp16 权重 | 4bit 权重 | 16 GB 可行性（fp16） | 16 GB 可行性（4bit） |
|---|---|---|---|---|
| 1.5B | 约 3.0 GiB | 约 0.9 GiB | 可行，8K × 16 并发 | 可行，上下文与并发充裕 |
| 3B | 约 6.0 GiB | 约 1.8 GiB | 可行，8K × 8 并发 | 可行 |
| 7B | 约 14.2 GiB | 约 4.4 GiB | 不可行（仅 4K × 1） | 可行，8K × 8 并发 |
| 14B | 约 28 GiB | 约 8.4 GiB | 不可行 | 勉强可行，4K × 2 并发 |
| 32B | 约 64 GiB | 约 19 GiB | 不可行 | 不可行 |

> 表中并发数为工程估算值，须在 P1 阶段以实测替换。实测方法：固定模型与上下文，逐步提高并发至 OOM，取前一级作为上限。

#### 5.4.4 推理服务启动基线

以下参数为单卡 16 GB 环境的推荐起点，须固化进镜像的启动脚本，避免每次手工指定：

```
VLLM_ATTENTION_BACKEND=XFORMERS          # C4：强制非 FlashAttention 后端
--dtype=half                             # C3：不得使用 bfloat16
--gpu-memory-utilization 0.85            # 预留固定开销，防止 OOM
--max-model-len 8192                     # 由 §5.4.2 的 KV 账推算
--max-num-seqs 8                         # 与显存预算匹配的并发上限
```

调试阶段额外使用 `--enforce-eager` 关闭图捕获，以缩短启动时间并便于定位问题；性能测试阶段移除该参数。

### 5.5 存储治理

#### 5.5.1 目录契约

| 路径 | 内容 | 所有者 | 权限 | 备份 |
|---|---|---|---|---|
| `/home/<user>` | 个人代码、实验产物 | 本人 | 700 | 否 |
| `/srv/share/models` | 共享模型权重 | 管理员 | 755，组只读 | 是（元数据） |
| `/srv/share/datasets` | 共享数据集 | 管理员 | 755，组只读 | 是 |
| `/srv/share/cache/hf` | 框架级缓存 | 管理员 | 755，组只读 | 否（可重建） |
| `/srv/services` | 常驻服务的 compose 与配置 | 管理员 | 755 | 是 |
| `/var/log/volta` | 使用记录与审计日志 | 管理员 | 750 | 是（30 天） |

原则：共享目录只读，个人写入限于家目录。任何跨用户写入须经管理员，以避免权限污染与归属不清。

#### 5.5.2 配额

配额实现方式取决于文件系统类型（§2.1 待补）：

| 文件系统 | 手段 | 粒度 | 建议值 |
|---|---|---|---|
| XFS | project quota | 目录 | 每用户 100 GB，软限 90 GB |
| ext4 | 无目录级配额，退化为定期审计 | 无 | 月度 `du` 报表 + 人工干预 |
| ZFS | dataset quota | 数据集 | 同上 |

配额的目的不是限制研究，而是保证"某一人的数据增长不会导致服务不可用"。

#### 5.5.3 清理与归属

| 动作 | 触发 | 执行者 | 约束 |
|---|---|---|---|
| 缓存清理 | 缓存目录超阈值 | 管理员 | 仅清理可重建内容 |
| 大文件审计 | 每月 | 管理员 | 生成归属报表，不自动删除 |
| 删除 | 经所有者确认 | 所有者或管理员 | 删除前留存清单 |

#### 5.5.4 模型权重的重复问题

多人各自下载同一模型将造成数倍磁盘开销。治理方式为：共享目录保存一份只读权重，使用者通过符号链接或在框架中指定 `HF_HOME` 指向共享缓存读取。该方式同时对网络带宽友好。

### 5.6 服务暴露

#### 5.6.1 端口分配

| 使用者 | 端口段 | 用途 |
|---|---|---|
| 使用者 A | 8000–8099 | 推理服务与调试 |
| 使用者 B | 8100–8199 | 同上 |
| 使用者 C | 8200–8299 | 同上 |
| 系统服务 | 9000–9099 | 指标、代理、管理接口 |

规则：服务启动时显式指定端口，禁止使用框架默认端口；端口占用检查纳入启动脚本。

#### 5.6.2 监听范围

所有服务默认监听 `127.0.0.1` 或内网地址。禁止监听 `0.0.0.0` 并结合端口映射暴露至公网，原因在于推理接口普遍缺少认证，暴露即等同于授权。

#### 5.6.3 服务登记

任何预期运行超过 1 小时的常驻服务须登记，字段见附录 D.1。登记的作用有二：一是使显存占用可预期，二是故障时能快速定位责任人。

### 5.7 可观测性与审计

#### 5.7.1 指标体系

| 指标 | 定义 | 采集方式 | 阈值 |
|---|---|---|---|
| GPU 占用率 | 采样窗口内 `utilization.gpu` 时间加权均值 | DCGM 或 `nvidia-smi` 轮询 | 低于 30% 视为资源闲置 |
| 显存占用率 | 已用显存 / 总显存 | 同上 | 高于 90% 持续 10 min 告警 |
| 有效计算占比 | 扣除加载与空闲后的计算时长占比 | 使用记录 + 采样 | 目标 > 60% |
| 冲突次数 | 单位时间内发生的资源争抢事件数 | 入口脚本日志 | 每周 ≤ 提交数 5% |
| OOM 事件数 | 显存耗尽失败次数 | 服务日志 | 每周 ≤ 2 |
| 环境重建时长 | 干净环境重建至可用状态的耗时 | 重建验收记录 | ≤ 30 min |
| 平均恢复时间 MTTR | 故障发生至服务恢复的时长 | 事故记录 | ≤ 30 min |
| 存储使用率 | 已用 / 配额 | 配额查询 | 高于 90% 告警 |
| GPU 温度 | 核心温度 | `nvidia-smi` | 高于 85 ℃ 告警 |

#### 5.7.2 日志与留存

| 日志 | 内容 | 留存 |
|---|---|---|
| 使用记录 | 谁、何时、何任务、耗时 | 90 天 |
| 服务日志 | 常驻服务的启动与请求 | 30 天 |
| 系统日志 | 内核消息、驱动事件 | 90 天 |
| 审计日志 | 提权操作、账号变更 | 1 年 |

### 5.8 故障域与恢复

#### 5.8.1 故障模式分析

| 编号 | 故障模式 | 影响范围 | 检测手段 | 缓解 | 恢复 |
|---|---|---|---|---|---|
| F1 | 单进程显存溢出 | 单任务 | 进程日志 | 显存预算（§5.4） | 重试，降低并发 |
| F2 | 孤儿进程占用显存 | 全机 | `nvidia-smi` 与终端比对 | 会话保活规范 | 确认后终止进程 |
| F3 | 驱动异常（`Xid` 报错） | **全机 GPU** | 内核日志 | 避免非常规调用 | 见 §5.8.3 |
| F4 | 掉卡（`fallen off the bus`） | **全机 GPU** | `nvidia-smi` 失败 | 供电与散热保障 | 断电重启 |
| F5 | 磁盘写满 | 全机 | 配额告警 | 配额（§5.5.2） | 清理可重建内容 |
| F6 | 端口冲突 | 单服务 | 启动失败 | 端口规范（§5.6.1） | 更换端口并登记 |
| F7 | 依赖被破坏 | 单用户 | 导入失败 | 环境隔离（§5.2） | 按声明文件重建 |

F3 与 F4 是全机性故障，其共同特征是**无法通过软件手段隔离**（§2.2 C9）。对此类故障，体系的策略是"降低发生概率 + 压缩恢复时间"，而非"防止发生"。

#### 5.8.2 驱动故障判据

内核日志出现以下事件时应判定为驱动级故障，而非应用级错误：

| 事件 | 含义 | 处理 |
|---|---|---|
| `Xid 13` | 图形引擎异常 | 记录并观察，通常可恢复 |
| `Xid 31` | 非法显存访问 | 定位触发进程，记录堆栈 |
| `Xid 43` | GPU 停止处理 | 需重置或重启 |
| `Xid 48` | 不可纠正 ECC 错误 | 记录硬件信息，评估更换 |
| `Xid 62` | 内部微控制器停止 | 重启 |
| `Xid 79` | GPU 从总线脱落 | 断电重启 |

#### 5.8.3 恢复流程

```
1. 确认影响面：nvidia-smi 是否可用；不可用则进入第 4 步
2. 记录现场：dmesg -T | tail -200 重定向至 /var/log/volta/incident-<时间>.log
3. 尝试软恢复：终止占用进程 → nvidia-smi -r（如允许）→ 重新加载内核模块
4. 若模块无法卸载：重启主机
5. 恢复后验证：nvidia-smi -q 检查温度、功耗、ECC 计数；运行基线推理一次
6. 填写事故记录（附录 D.3）
```

#### 5.8.4 孤儿进程判定

判定规则须同时满足，避免误杀常驻服务：

| 条件 | 判定 |
|---|---|
| 进程无控制终端（`tty` 为空） | 必要条件 |
| 父进程为 1 | 必要条件 |
| 运行时长超过阈值（建议 12 小时） | 必要条件 |
| 未出现在服务登记表中 | 充分条件 |
| 持有进程内无活动（GPU 利用率持续为 0） | 辅助条件 |

仅当上述必要条件与"未登记"同时成立时，方可在通知所有者后终止。**常驻推理服务不得纳入自动清理范围**，此类服务天然满足前三项条件。

### 5.9 变更管理

#### 5.9.1 变更分级

| 级别 | 范围 | 审批 | 记录 | 回滚 |
|---|---|---|---|---|
| L1 用户级 | 个人环境、个人代码 | 无需 | 自留 | 自行处理 |

在小规模团队中，管理员与使用者可为同一人兼任，但两种角色在记录中必须区分，否则审计失效。

### 6.2 使用规约

正式规约见 `docs/usage-rules.md`。本节仅确立其效力来源：规约由全体使用者确认后生效，修订须经全体知情；违反规约导致的资源损失由当事人承担恢复成本。

### 6.3 准入与退出

| 阶段 | 检查项 | 完成标志 |
|---|---|---|
| 准入 | 账号已建、规约已读、端口段已分配、环境已自建并验收 | 台账记录完成 |
| 退出 | 数据已移交、服务已停止、账号已锁定 | 台账记录完成 |

### 6.4 事故分级

| 级别 | 定义 | 响应时限 | 复盘要求 |
|---|---|---|---|
| S1 | 全机 GPU 不可用 | 30 min | 必须复盘 |
| S2 | 多人任务中断 | 2 h | 必须复盘 |
| S3 | 单人任务失败 | 1 个工作日 | 记录即可 |
| S4 | 性能下降或配置偏差 | 1 周 | 记录即可 |

### 6.5 度量评审

每月对 §7 的指标做一次评审，输出两项结论：一是当前阶段是否达到退出标准，二是下一阶段的进入条件是否已满足。评审记录归入仓库，作为演进决策的证据。

## 7 度量体系

目标值为初始假设，须在运行四周后以实测数据校准。校准前不得以此作为考核依据。

| 指标 | 计算方式 | 初始目标 | 采集频率 | 用途 |
|---|---|---|---|---|
| GPU 时间利用率 | 计算时长 / 统计周期 | 40% 以上 | 每日 | 判断是否需要扩容或引入调度 |
| 有效计算占比 | （计算时长 − 加载 − 空闲）/ 计算时长 | 60% 以上 | 每周 | 判断服务化是否充分 |
| 冲突率 | 冲突事件数 / 任务提交数 | 5% 以下 | 每周 | 判断入口机制是否有效 |
| OOM 事件数 | 显存耗尽次数 | 每周 2 次以下 | 每周 | 判断显存预算是否合理 |
| 环境重建时长 | 重建验收实测值 | 30 min 以内 | 每次变更 | 验证 G1 |
| 平均恢复时间 | 故障至恢复的平均时长 | 30 min 以内 | 每次事故 | 验证 G4 |
| 存储使用率 | 已用 / 配额 | 90% 以下 | 每日 | 预警磁盘风险 |
| 未登记服务数 | 巡检发现的未登记常驻服务 | 0 | 每两周 | 验证治理有效性 |

指标的使用原则：指标用于发现体系缺陷，不用于评价个人。若某指标持续劣化，应首先检视机制设计，而非归因于使用者。

## 8 演进路线与阶段门限

每个阶段的进入由可观测条件触发，避免在收益不足时引入复杂度。阶段之间不要求全部完成前一阶段，但不得跳过前提条件。

| 阶段 | 目标 | 交付物 | 进入条件 | 退出标准 |
|---|---|---|---|---|
| P0 基座 | 建立最低限度的秩序与可追溯性 | 账号体系、资产台账、目录契约与配额、统一入口、`gpustat`、使用记录 | 硬件到位 | §7 中冲突率、OOM、存储三项达到目标 |
| P1 隔离与服务化 | 环境可复现，推理服务共享 | 镜像基线、Ansible 初始化、DCGM 指标栈、服务登记制度、预约机制 | 出现"环境被破坏"事件 ≥ 2 次/月，或有效计算占比 < 50% | 环境重建时长 ≤ 30 min，未登记服务数为 0 |
| P2 调度与配额 | 资源分配由机制而非纪律保证 | Slurm 单机（GRES）、按用户时长配额、可选 JupyterHub 入口 | 冲突率 > 10% 持续两周，或出现"占卡导致他人任务延期超过 1 天" | 冲突率 ≤ 5%，排队时长可预期 |
| P3 硬件演进 | 扩容或更换 | 新硬件接入方案、迁移方案 | 该卡生态支持终止（约 2028 年），或负载持续超出容量 | — |

关于 P2 的说明：Slurm 在单卡环境的实质收益是"强制"而非"调度"——把依赖纪律的互斥升级为调度器保证的互斥。若 P1 的预约机制已能使冲突率达标，则 P2 不必实施；过度引入调度器会显著降低交互式开发效率，属于净损失。
